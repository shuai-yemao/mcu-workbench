# BRD：Platform / Impl OS 实践工程对齐

## 1. 背景与目标

插件当前 OS Skill 沿用 `osal_*` / `os_*_impl()` 术语，而实践工程已经采用 `platform_os_*` / `impl_os_*` 的 Platform/Impl 命名。两者都表达“Platform 契约 → Impl Port → FreeRTOS”的两层关系，但文档、测试和案例会给出不同的落地名称。用户已明确旧命名不兼容。

本需求的目标是让插件能够基于真实嵌入式工程指导 OS 分层、命名和验证，同时保持行为契约不被文档更新悄然改变。

## 2. 价值

- 让插件输出的文件名、include、函数和宏名与实践工程一致，并彻底停止输出旧命名。
- 让 Platform OS 与 Impl OS 的依赖方向可以从文档直接还原。
- 把破坏性迁移记录、实践命名和未验证行为明确分区。
- 让测试、架构图谱和 Skill 正文不会互相矛盾。

## 3. 非功能约束

- 只更新插件文档、参考资料、架构索引和测试契约；不复制固件源码。
- 不把静态审查、主机测试或实践工程扫描描述为目标板通过。
- 保留现有工作区未提交修改，不使用全量暂存。
- 所有新增案例必须标注 `confirmed`、`user-confirmed`、`inferred` 或 `unverified`。

## 4. 风险

最大风险是把实践工程当前候选实现中的类型、错误码、ISR 或接口差异误写成命名规范。该风险通过“命名证据与行为证据分离”、token 对账和最终独立 Review 关闭。

## 5. 决策门槛

在完成 109 规划与实践工程实际符号的对账前，不进入 Skill 修改阶段。旧命名兼容决策已关闭，结论为不兼容。
