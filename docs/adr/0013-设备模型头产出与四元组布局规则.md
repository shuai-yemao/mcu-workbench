# ADR-013: 设备模型头产出与四元组布局规则

## Status
Accepted（2026-08-10）

## Context
对实例文件 `watch_device.h`（EC-S100 手表设备模型，聚合 IMU/温湿度/电池/背光 4 设备）与插件 skills 对比，发现：

1. **契约缺口**：`platform_bsp` 输出契约只有 wrapper（`platform_<type>_wrapper.h`：转发实现 + 注册），没有"设备模型"独立产出物——"设备长什么样"（类型契约）与"设备怎么落地"（转发实现）未分离。模型是芯片无关的契约，本应"接口永不改"，却与可换的转发实现耦合。
2. **布局不一致**：四元组模板写 `ctx/data = 指针`（`xxx_ctx_t *`），而实例用**内联值**（`motion_ctx_t ctx`）。内联与 device"继承式内联扩展"哲学（自包含、类型安全、实例少且静态分配）一致——模板的"指针"表述反而与之矛盾，生成器会困惑。
3. **ops 签名冲突认知**：实例 ops 首参是具体设备指针（`imu_device_t *`），模板 `pf_*` 首参是 `void *context`——两者其实是"两层 ops"，文档未区分导致看起来打架。
4. **可吸收模式**：实例的通用/厂商双 typedef（`motion_cfg_t` ↔ `imu_data_t`）展示了"稳定抽象 + 可变别名"——换芯片只改别名，上层零改动。

## Decision

1. **设备模型头为独立产出物**：`platform_bsp` 输出 `platform_<type>_model.h`——只含四件套类型（`<type>_cfg_t / <type>_ctx_t / <type>_data_t / <type>_ops_t`）、设备对象 struct（base 首字段 + 四槽）、`platform_<type>_init()` 声明。**零芯片依赖、不含转发实现**。生成流程改为三步：**模型头 → wrapper → 注册**。
2. **四元组布局规则**：`cfg` = `const *`（共享配置）、`ops` = `const *`（共享行为表）、`ctx` = **内联值**（实例独有状态）、`data` = **内联值**（实例独有数据）。判断句：**"共享的用指针，独有的用内联"**。service 继续用指针槽（`platform_service_t` 已内嵌）。
3. **两层 ops 签名**：
   - **模型 ops**（模型头内）：首参**具体设备指针**（`imu_device_t *p_dev`），裸名（`read`/`sleep`）——Service 层类型安全调用；
   - **转发表 ops**（wrapper 内）：`pf_*` 首参 `void *context`——Impl 注册、manager 统一驱动。
4. **通用/厂商双名**（可选约定）：`<type>_cfg_t` 等为通用主体类型；厂商型号别名（如 `mpu6050_cfg_t = imu_cfg_t`）用于换芯片只改别名映射。非强制（YAGNI 平衡）。
5. **四件套命名显式化**：`<type>_cfg_t / <type>_ctx_t / <type>_data_t / <type>_ops_t` 为生成强制命名，工具链/grep/文档可依赖。

## Consequences

**变容易**
- 模型先行（Model-first）：先定"设备长什么样"（类型契约），再谈转发实现——与 Service 工作流"先 `_model` 后实现"对齐；
- Service 直接 include 模型头，不依赖 wrapper（模型头是"接口永不改"的契约，wrapper 可换实现）；
- 布局规则可教可查："共享的用指针，独有的用内联"；
- 换芯片/换 IMU 型号：只改厂商别名映射，上层零改动。

**变困难**
- 每设备多一个产出物（`model.h` + `wrapper.h`）——文件数增加，但换来契约与实现分离；
- 模型 ops 裸名与 wrapper `pf_` 并存，需文档说清两层差异（模板 v2 已补）；
- 旧代码若用 ctx/data 指针形态，迁移到内联需逐步进行（模板 v2 带兼容说明）。
