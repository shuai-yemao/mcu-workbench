# 嵌入式项目 C/C++ 编码规范

> 本规范由 tools-quality 承接为全项目代码质量基线，适用于 AI 生成、代码生成器产物、人工新增、人工修改和已有代码重审。
> 其中命名、函数、注释和排版规则均适用于插件所有生成代码；FreeRTOS/内核源码仅作为排版基线的来源，不限定适用模块。
> 本规范整合命名规范、头文件模板、Doxygen 注释规范、代码排版规则和通用质量原则；顶层架构以
> [`software-layer-contract.md`](../../../workflow/workflow-review-gate/references/software-layer-contract.md) 为唯一来源。

## 硬性约束（违反即错误）

| # | 规则 | 正确 | 错误 |
|---|------|------|------|
| 1 | 使用 TAB 缩进，并保持连续声明组的列对齐 | `\tif (x == 0)` | 用空格替代统一缩进 |
| 2 | 代码和注释均不得超过 80 列 | 每行显示宽度不超过 80 列 | 任意代码或注释超过 80 列 |
| 3 | 返回值必须检查 | `ret = func(); if (OK != ret)` | `func();` |
| 4 | 指针有效性必须按契约判定 | 外部可为空边界执行 `if (NULL == p_data)` | 未确认可用性就解引用 |
| 5 | 判断时常数放左边 | `if (0 == ret)` | `if (ret == 0)` |
| 6 | 公共 `.h` 中每个函数声明有完整 Doxygen；`.c` 中核心函数有完整 Doxygen | `/** @brief ... */` | 公共接口或核心函数缺少必要说明 |
| 7 | `.c` 中复杂或非显然逻辑使用必要的段注释；简单函数不机械添加 | `/* 步骤说明 --- */` | 关键逻辑无说明或生成无意义注释 |
| 8 | 注释语言按注释类型和对齐约束确定：Doxygen、文件/段/函数内必要说明默认使用中文；需要同时对齐起始列和结束列的连续行尾注释默认使用简短、直白的英文 | `/* Operation OK. */` | 需要右边界对齐时使用复杂英文或不同长度的中文说明 |
| 9 | 同组声明、赋值和初始化符号对齐 | `uint32_t value = 0U;` | 同组列未对齐 |
| 10 | 同一连续代码组的行尾注释起始列和结束列对齐 | `member_a;    /* Short description. */` | 行尾注释参差不齐 |

## 命名规则

命名必须尽可能可读、可搜索、名副其实，并使用所涉问题领域的正式名称。一个概念只能对应一个稳定词汇；不得使用双关语、含义模糊的泛化词或为了区分而制造无意义差异。

### 新生成文件与已有文件修改边界

- 新生成的 `.c/.h` 文件必须完整遵循本节规则。
- 修改已有文件时，必须保留已有文件名、公开 API 和无关区域；只约束本次修改的函数、代码块和新增符号。
- 不得自动重命名已有文件、公开函数、公开类型或公开宏，不得对无关区域做全文件命名重构。
- 如果新增符号无法与既有模块命名形成唯一、可搜索且不误导的名称，必须阻塞并回传冲突，不得猜测。

### 文件命名

新文件使用 `<layer>_<module>_<role_or_feature>.h/.c`，不强制添加项目简称：

| 层级 | 文件格式 | 示例 |
|------|----------|------|
| App | `app_<module>_<feature>.h/.c` | `app_sensor_monitor.c` |
| Service | `service_<module>_<feature>.h/.c` | `service_sensor.c` |
| Platform | `platform_<module>_<feature>.h/.c` | `platform_sensor.h` |
| Impl | `impl_<module>_<role>.h/.c` | `impl_sensor_driver.c` |
| Vendor | `vendor_<module>_<feature>.h/.c` | `vendor_sensor_hal.c` |

允许的特殊文件后缀只有：

```text
_driver
_handle
_port
_config
```

禁止新生成以下文件后缀：

```text
_wrapper
_model
_state
_fault_code
```

数据模型、状态定义和故障码应放入所属模块的主头文件/源文件；`_config` 仅用于确实需要独立配置边界的文件。已有文件保留原名，不因本规则自动迁移。

### 符号命名

| 对象 | 规则 | 示例 |
|------|------|------|
| 对外函数 | `<layer>_<module>_<action>()` | `platform_sensor_read_temperature()` |
| 内部 `static` 函数 | `<module>_<action>()` | `sensor_validate_config()` |
| 局部变量 | `snake_case` | `temperature_celsius` |
| 全局变量 | `g_<name>` | `g_sensor_registry` |
| 文件静态变量 | `s_<name>` | `s_sensor_state` |
| 指针变量 | `p_<name>` | `p_sensor_config` |
| 函数指针 | `pf_<name>` | `pf_sensor_callback` |
| 宏 | `UPPER_SNAKE_CASE` | `SENSOR_TIMEOUT_MAX_MS` |
| 枚举/结构体类型 | `<module>_<name>_t` | `sensor_config_t` |
| 枚举项 | `UPPER_SNAKE_CASE` | `SENSOR_STATUS_READY` |
| 结构体成员 | `snake_case` | `timeout_ms` |

### 可读性、搜索性和领域语义

- 名称应能直接读出含义，优先使用 `temperature`、`humidity`、`register`、`timeout`、`callback` 等领域词。
- 同一概念不得混用同义词或缩写，例如统一使用 `buffer`、`config`、`timeout`、`callback`，不得在新增代码中混用 `buf`、`cfg`、`wait_time`、`cb`。
- 行业通用缩写 `i2c`、`uart`、`dma`、`isr`、`rtos`、`bsp`、`hal` 可以保留；非通用缩写必须先在项目规则中确认。
- 名称必须包含必要语境，明确模块、对象、方向、单位、用途或所有权，例如 `uart_rx_buffer`、`timeout_ms`、`p_owned_buffer`。
- 禁止使用无法表达职责的名称，例如 `data`、`info`、`item`、`object`、`thing`、`misc`、`util`、`do_work`、`process_data`。
- 名称必须准确描述实际职责；函数不承担名称之外的隐含职责，不得用 `manager`、`task`、`wrapper` 等词掩盖普通转发或局部处理。
- 名称之间的差异必须对应真实差异，例如区分 `raw_temperature`/`temperature_celsius`、`timeout_ms`/`timeout_ticks`、`rx_byte_count`/`rx_item_count`。

### 分层命名策略

| 层级 | 前缀 | 职责 |
|------|------|------|
| App 层 | `app_{功能}_` | 场景编排、Task、Logic、UI |
| Service 层 | `service_{模块}_` | 面向业务的稳定服务和策略 |
| Platform 层 | `platform_{模块}_` | 能力接口、统一类型、错误码和对象协议 |
| Impl 层 | `impl_{模块}_` | Platform 接口的具体实现和资源绑定 |
| Vendor 层 | `vendor_{模块}_` | 芯片厂商库、SDK、HAL、LL 或第三方底层实现 |

固定依赖方向为：

```text
App → Service → Platform 接口 ← Impl → Vendor
```

App 不得直接依赖 Platform 的具体实现、Impl、Vendor、HAL、RTOS 或芯片寄存器。

### 外设变量命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 缓冲区 | `{模块}_{用途}_buffer` | `uart_rx_buffer` |
| 句柄 | `{外设}_handle` | `i2c1_handle` |
| 寄存器 | `{模块}_reg_{描述}` | `mpu6050_reg_who_am_i` |
| 引脚 | `{功能}_pin` | `led_pin`, `btn_pin` |
| 超时 | `{模块}_timeout_{单位}` | `i2c_timeout_ms` |
| 标志位 | `{模块}_flag_{描述}` | `bsp_flag_data_ready` |
| 状态机 | `{模块}_state_{状态}` | `app_state_idle` |
| 错误 | `{模块}_err_{类型}` | `bsp_err_i2c_timeout` |

## 头文件模板

```c
/******************************************************************************
 * Copyright (C) 2024 EternalChip, Inc.(Gmbh) or its affiliates.
 *
 * All Rights Reserved.
 *
 * @file {layer}_{module}_{role_or_feature}.h
 *
 * @par dependencies
 * - {dependency_header_1}
 * - {dependency_header_2}
 *
 * @author Jack | R&D Dept. | EternalChip
 *
 * @brief {Provide the module function description.}
 *
 * @version V1.0 {YYYY-MM-DD}
 *
 * @note 1 tab == 4 spaces.
 *
******************************************************************************/

#ifndef __{LAYER}_{MODULE}_{ROLE_OR_FEATURE}_H__
#define __{LAYER}_{MODULE}_{ROLE_OR_FEATURE}_H__

/* 包含文件 --------------------------------------------------------------------- */
#include <stdint.h>
#include <stdbool.h>

/* 公开宏定义 ------------------------------------------------------------------- */

/* 默认值 ------------------------------ */

/* {MODULE} 寄存器/位宏定义说明 ------------------------------------------------------ */
#define {MODULE}_REG_XXX          0x00
#define {MODULE}_BIT_XXX          0

/* 枚举类型 --------------------------------------------------------------------- */

/**
 * @brief {模块} 操作状态枚举
 */
typedef enum
{
    {MODULE}_OK      = 0, /* 操作成功。 */
    {MODULE}_ERROR,       /* 通用错误。 */
    {MODULE}_TIMEOUT      /* 操作超时。 */
} {module}_status_t;

/* 结构体类型 -------------------------------------------------------------------- */

/**
 * @brief {模块} 初始化配置结构体
 */
typedef struct
{
    uint8_t member;       /* {成员说明} */
} {module}_config_t;

/* 公开函数 --------------------------------------------------------------------- */
/* 初始化 ------------------------------ */
{module}_status_t {层}_{模块}_init(const {module}_config_t *p_config);

/* 读写 ------------------------------- */
{module}_status_t {层}_{模块}_read_reg(uint8_t reg, uint8_t *p_data);
{module}_status_t {层}_{模块}_write_reg(uint8_t reg, uint8_t data);

#endif /* __{LAYER}_{MODULE}_{ROLE_OR_FEATURE}_H__ */
```

### 头文件组织顺序

1. 文件头注释 → 2. 包含保护 → 3. 标准库 → 4. 项目头文件 → 5. 宏定义 → 6. 枚举 → 7. 结构体 → 8. 函数指针 → 9. 函数声明

## 函数结构模板

## 函数设计硬规则

以下规则适用于新生成函数，以及已有文件中本次修改的函数；不授权自动重构无关函数或修改已有公开 API。

1. **短小优先**：函数只保留完成当前职责所需的语句；能够继续下沉或删除的语句必须继续缩短函数。
2. **还要更短小**：当函数已经能够工作时，继续检查是否可以拆出更清晰的下一层函数；不得以“代码量不大”为由保留混合职责。
3. **DO ONE THING**：一个函数只做一件事，并且只有一个修改原因。函数名如果需要使用“并且”连接两个动作，通常必须拆分。
4. **同一抽象层级**：函数内的语句必须处于同一抽象层级；高层流程不得与寄存器位操作、字节编解码、日志格式化或资源释放细节混在一起。
5. **逐层下降**：函数按由高到低的抽象顺序组织；每个函数后面应紧跟它调用的下一抽象层级函数，使代码能够从上到下阅读。
6. **描述性名称**：函数名必须准确描述唯一职责和领域动作，不使用 `process`、`handle`、`do_work` 等不能说明具体行为的名称。
7. **参数尽量少**：参数数量以 0 个为理想目标，通常不超过 1 个；2 个及以上必须有明确的领域理由和审查记录，3 个及以上的新函数默认阻塞。不得用无语义的结构体或上下文参数掩盖过多、不相关的输入。
8. **禁止重复**：相同的业务规则、校验、转换或错误处理不得在多个函数中复制；应提取为具有领域名称的下一层函数。不得为了消除几行重复而创建 `util`、`common` 等无语义泛化函数。

```c
/**
 * @brief   {一句话描述}
 * @param   {name} [in/out] {说明}
 * @retval  {MODULE}_OK     成功
 * @retval  {MODULE}_ERROR  失败
 * @note    {使用注意事项}
 * @warning {调用前提条件或危险场景}
 * @see     {关联函数交叉引用}
 */
{module}_status_t {层}_{模块}_{动作}({参数列表})
{
    {module}_status_t ret;
    uint8_t           local_var;

    if (NULL == p_data) {
        return {MODULE}_ERROR;
    }

    ret = {底层函数调用}();
    if ({MODULE}_OK != ret) {
        return ret;
    }

    /* 该转换必须在发送前完成，避免底层接口接收错误单位。 */

    return {MODULE}_OK;
}
```

**注释格式规则：**

- 文件头必须使用参考文件的 `/*****************************************************************************/` 块格式；字段顺序固定为版权、保留声明、`@file`、`@par dependencies`、`@author`、`@brief`、`@version`、`@note`
- 文件头版权固定为 `EternalChip`，作者字段固定为 `Jack | R&D Dept. | EternalChip`；文件名、依赖、摘要和版本日期按文件实际内容填写
- 文件头依赖项使用 `- - {dependency}` 形式；没有依赖时使用 `- - None.`
- 文件头不再强制添加“处理流程”字段；具体流程只在核心函数或复杂代码块中说明
- 注释语言按注释类型和对齐约束确定：Doxygen、文件/段/函数内必要说明默认使用中文；需要同时对齐起始列和结束列的连续行尾注释默认使用简短、直白的英文。英文行尾注释使用常用词、直接表达实际含义，不使用习语、长句或生僻缩写；复杂语义仍放在中文 Doxygen 或块注释中。用户或项目明确指定语言时优先遵从指定
- 段注释文字左对齐，紧跟 `/* ` 之后
- 一级文件分区使用 80 列横线，二级分区使用 60 列横线，三级分区使用 40 列横线
- 宏定义使用对应层级的段注释，不得混用分区长度
- 普通行尾说明使用 `/* Short description. */`，不使用 `/**< Short description. */`
- 同一连续枚举、结构体、宏、初始化或函数指针声明组内，行尾注释的起始列和结束列必须对齐；此类需要右边界对齐的注释默认使用简短、直白的英文
- 函数内部注释统一使用 `/* ... */`；同一连续注释组的起始列和结束列必须对齐
- 函数内部不得使用 `//` 代替块注释；注释内容过长时拆分为独立的 `/* ... */` 注释块
- 行尾注释对齐不得跨越空行、分区注释或不同代码块；超过行宽时优先换成独立注释
- 函数内每个逻辑块之间空一行
- Doxygen 注释中 `@tag` 统一缩进 2 个空格

**函数注释适用范围：**

- 公共头文件中的每个对外函数声明必须有完整 Doxygen，至少包括 `@brief`、全部 `@param` 和适用的 `@retval`
- 私有头文件中的内部函数声明不强制完整 Doxygen；若参数、返回值或前置条件不显然，补充简短说明。私有头文件应能通过路径或文件名中的 `private`、`priv` 或 `internal` 标识识别，否则按公共头文件处理
- `.c` 中实现公共 API 的函数，以及初始化、反初始化、状态机、任务循环、硬件事务、协议处理、ISR/DMA/回调、资源生命周期、错误恢复和复杂算法函数，视为核心函数，必须有完整 Doxygen
- `.c` 中的普通函数必须按长度、控制流、调用数量、资源/错误风险和语义显然程度分级：简单且自解释的函数不写函数头注释；有一个非显然约束时只写一条必要的 `/* ... */` 说明；只有复杂或高风险函数才写完整 Doxygen
- `.c` 函数不得因为“存在返回值”“调用了其他函数”或“属于 static 函数”就机械添加完整注释；注释必须能降低理解成本
- 同一 `.c` 文件中语义、参数约束、返回结果和执行上下文基本相同的函数属于相似函数族：示例输出只展示一个代表性完整注释，其他函数只说明自身差异，不重复复制相同段落
- 实际源码中，相似核心函数仍需保留各自必要的函数契约；公共的所有权、阻塞、并发或硬件约束可引用函数族说明，不得重复堆叠相同句子
- 完整 Doxygen 重点说明参数、返回值、所有权、生命周期、单位、范围、阻塞属性、执行上下文、并发限制、硬件约束和错误恢复；不逐行翻译函数体
- `@note`、`@warning`、`@see` 仅在实际适用时添加，不机械补齐

**生成代码的函数内部注释契约：**

- 生成器只为公共 `.h` 声明和核心 `.c` 函数生成完整函数注释；私有头文件和简单 `.c` 函数不得机械补齐完整 Doxygen。
- 生成器根据函数名、控制流、调用数量以及 ISR/DMA/回调/资源/错误等风险信号判断 `.c` 函数是否为核心函数；判断结果不能替代人工审查。
- 对简单 `static` 辅助函数，生成器不添加函数头 Doxygen；只有语义不显然时保留局部必要说明。
- 对相似 `.c` 函数，生成器和示例输出不得重复生成相同的说明段落；只为当前函数补充独有的参数、返回值、资源或错误差异。
- 函数内部不自动生成“状态”“转发”“校验”“结果”“处理”等泛化阶段标题或重复说明。
- 只有存在非显然的硬件时序、所有权、生命周期、并发、缓存/DMA、错误恢复或算法原因时，才补充 `/* ... */` 说明。
- 生成器输出必须经过本规范的 `.clang-format` 和注释门禁；不得用重复性阶段注释代替真实语义。

**已有代码文件修改契约：**

- 已有 `.c/.h` 文件的文件名、公开 API 和无关区域必须保留，不得为了套用新规则自动重命名或全文件重排。
- 只对本次修改的函数、代码块和新增符号执行本规范的命名、注释和格式检查。
- 既有注释的有效语义必须保留；只有本次修改涉及的注释和缺失的新增 API 标签需要整改。
- 同一 `typedef enum/struct` 或连续代码块内，声明、赋值、初始化符号以及行尾注释必须分别对齐；对齐不能跨越空行、分区注释或不同代码块。
- 任何本次修改结果都必须满足 80 列硬上限；若目标工程提供更严格的格式配置，以更严格配置为准，不得修改无关区域。

## 注释类型速查

| 注释类型 | 格式 | 示例 |
|----------|------|------|
| 文件头注释 | 版权与 Doxygen 组合模板 | `@file`/`@brief`/`@author`/`@version` 必填 |
| 公共 API Doxygen | 公共 `.h` 函数声明 | `@brief` + `@param` + 适用的 `@retval` |
| 核心函数 Doxygen | `.c` 核心函数定义 | `@brief` + `@param` + 适用的 `@retval` |
| 普通 `.c` 函数 | 按复杂度判断 | 仅在语义不显然时添加简短说明 |
| 枚举/结构体 | 类型块注释 + 普通行尾注释 | `/** @brief */` + `/* Member description. */` |
| 宏定义 | 段注释 | `/* 宏说明 ----------------- */` |
| 函数内必要说明 | 两侧对齐的普通块注释 | `/* DMA 缓冲区必须位于可访问内存。 */` |
| 行尾说明 | 对齐的普通行尾注释 | `member;    /* Short description. */` |

## 枚举与结构体注释

```c
/**
 * @brief {模块} 操作状态枚举
 */
typedef enum
{
    {MODULE}_OK      = 0, /* 操作成功。 */
    {MODULE}_ERROR,       /* 通用错误。 */
    {MODULE}_TIMEOUT      /* 操作超时。 */
} {module}_status_t;

/**
 * @brief {模块} 初始化配置结构体
 */
typedef struct
{
    uint8_t  member1;     /* {成员说明} */
    uint16_t member2;     /* {成员说明} */
} {module}_config_t;
```

## 代码排版细节

| # | 规则 | 示例 |
|---|------|------|
| 1 | 使用 TAB 缩进，并保持连续声明组的列对齐 | `\tif (0 == ret)` |
| 2 | 代码和注释不超过 80 列 | 每行显示宽度不超过 80 列 |
| 3 | 函数大括号 `{` 换行独行 | `void func(void)\n{` |
| 4 | `if/for/while` 大括号 `{` 换行独行 | `if (0 == ret)\n{` |
| 5 | 枚举/结构体大括号 `{` 换行独行 | `typedef enum\n{` |
| 6 | 二元运算符两侧加空格 | `a + b`, `ret == OK`, `x = y` |
| 7 | 一元运算符不空格 | `*p_data`, `&var`, `!flag`, `~mask` |
| 8 | `,` `;` 后加空格 | `func(a, b)`, `for (i = 0; i < n; i++)` |
| 9 | 括号内不加空格 | `func(a, b)` 不写 `func( a, b )` |
| 10 | 指针 `*` 靠变量名 | `uint8_t *p_data` |
| 11 | 判断时常数放左边 | `NULL == p`, `0 != (mask & val)` |
| 12 | 函数间空一行 | 两个函数定义之间一个空行 |
| 13 | 逻辑块间空一行 | 步骤注释前保留一个空行 |
| 14 | 同组声明的类型、变量名和 `=` 分列对齐 | `uint32_t value = 0U;` | 声明列不对齐 |
| 15 | 同组赋值语句的 `=` 对齐 | `p_data->value = x;` | 赋值列不对齐 |
| 16 | 同一连续代码组的行尾注释起始列和结束列对齐；需要右边界对齐时默认使用简短英文 | `member_a;    /* Short description. */` | 注释列不对齐 |

### 声明、赋值和初始化对齐

对齐只作用于同一连续代码组或同一个 `typedef enum/struct`，不跨越空行、注释、函数步骤分区、逻辑分区或不同声明组。
对齐必须服从 80 列硬上限；行尾注释右边界不得为了对齐超过第 80 列，超过时应缩短英文说明或改为独立注释块。

```c
/* 变量声明组 ------------------------- */
uint32_t timeout_ms  = 0U;
uint32_t retry_count = 0U;
bool     is_ready    = false;

/* 赋值语句组 -------------------------- */
p_data->temperature = sensor_convert_temperature(p_data->raw_temperature);
p_data->humidity    = sensor_convert_humidity(p_data->raw_humidity);

/* 枚举值组 ---------------------------- */
typedef enum
{
    SENSOR_STATE_IDLE    = 0,
    SENSOR_STATE_RUNNING = 1,
    SENSOR_STATE_ERROR   = 2,
} sensor_state_t;

/* 指定初始化组 ------------------------ */
sensor_config_t config =
{
    .timeout_ms  = SENSOR_TIMEOUT_MS,
    .retry_count = SENSOR_RETRY_COUNT,
    .is_enabled  = true,
};
```

结构体成员没有初始化符号时，只对齐类型和成员名；如果成员存在行尾注释，注释起始列也必须在该类型定义内对齐：

```c
typedef struct
{
    uint8_t  raw_value;
    uint16_t sample_count;
    bool     is_valid;
} sensor_data_t;
```

对齐规则不要求不同代码块之间使用相同列位置；每个代码块独立计算对齐列。

## 统一嵌入式源码排版 profile

插件默认使用 [`quality-format-check/.clang-format`](capabilities/quality-format-check/.clang-format)。
该 profile 将审查过的 FreeRTOS/内核源码排版特征作为所有插件生成代码的统一基线；它不把
FreeRTOS 的注释内容、命名方式、函数设计或内核语义提升为额外规则。

### 适用的排版特征

- 使用 TAB 表示缩进，并使用 TAB/空格保持类型、成员名和连续声明组的列对齐。
- 结构体、枚举、函数和控制语句使用 Allman 大括号：左大括号独占下一行。
- 条件编译指令按嵌套层级缩进；同一条件编译块的 `#if` 与 `#endif` 保持层级对齐。由于 clang-format 对预处理指令有独立处理逻辑，该项需要人工复核。
- 成员声明、条件编译区域和逻辑分组之间使用空行分隔；同一成员组内部不机械插入空行。
- 指针 `*` 靠近变量名；括号和赋值运算符遵循该 profile 的 clang-format 配置。
- 代码和注释统一遵守 80 列硬上限；若目标工程明确提供更严格的 `.clang-format`，以更严格配置为准。

示例：

```c
typedef struct tskTaskControlBlock
{
	volatile StackType_t *pxTopOfStack;

#if ( portUSING_MPU_WRAPPERS == 1 )
	xMPU_SETTINGS xMPUSettings;
#endif

	ListItem_t  xStateListItem;
	UBaseType_t uxPriority;

#if ( configUSE_MUTEXES == 1 )
	UBaseType_t uxBasePriority;
	UBaseType_t uxMutexesHeld;
#endif

} tskTCB;
```

插件生成的所有 `.c/.h` 文件默认使用该 profile；命名、函数结构、Doxygen、必要逻辑注释和格式均为硬门禁。
凡是插件规则、生成流程或插件交接任务明确要求修改的既有文件，本次涉及的文件名、函数、代码块、新增符号和注释
也必须完整使用本 profile，不得以既有文件风格或较宽松的工程配置豁免。未被插件要求修改的既有区域只保留为基线，
不扩大重排范围；目标工程更严格的规则可以叠加。

## 九大核心原则

### 1. 架构先行
先读取并遵循 [`software-layer-contract.md`](../../../workflow/workflow-review-gate/references/software-layer-contract.md)，
再编写或修改代码。该文件是全项目顶层架构、依赖方向和 Platform/Impl/Vendor 边界的唯一来源；本 profile
只规定代码表达方式，不复制一套可能过时的架构设计。质量审查至少确认：
- App 只调用 Service 公开接口；
- Service 承载业务策略并依赖 Platform 公共契约；
- Platform 定义能力接口、统一类型、错误码和对象协议，不反向依赖 Impl；
- Impl 负责具体资源绑定、生命周期和后端适配；
- Vendor 只作为底座，由 Impl 接入；
- OS/BSP 的 Wrapper、Port、Driver、Handle 等是 Impl/Platform 内部角色，不能被提升为另一套顶层架构。

### 2. 接口契约
模块之间通过函数签名通信：
- 统一返回模块自己的 `{module}_status_t` 枚举
- 输入参数加 `const`，输出参数用指针
- doxygen 注释标注 `[in]`/`[out]`/`[in/out]`

### 3. 命名一致性
严格遵循本技能的命名规则；同一概念使用同一词汇，名称必须可读、可搜索、名副其实且带有必要语境。

### 4. 函数设计
函数必须短小、只做一件事、处于单一抽象层级，并按由高到低的抽象顺序排列；参数以零个为理想目标，重复逻辑必须消除。

### 5. 增量验证
每次只生成一个函数，编译通过后再继续。
绝不一次生成整个模块。

### 6. 文档即代码
每个头文件有模块注释；公共 `.h` 中每个对外函数声明和 `.c` 中每个核心函数有完整 Doxygen。
代码即文档，文档即代码。

### 7. 内存安全
所有缓冲区在作用域内有效：
- DMA 缓冲区使用静态/全局内存，禁止用栈上局部变量
- RTOS 任务栈留有 20% 余量，并结合 HighWaterMark、峰值路径和异常路径验证
- 数组访问前索引判界
- 指针是否判空由接口契约、生命周期、所有权和可选性决定；不得机械地对所有指针重复判空
- 公共 API 或外部输入边界对可能为空的必需指针必须判空并返回明确错误
- 已在更高层边界验证为有效的内部必需指针，必须记录前置条件，不得重复添加无意义的判空
- 指针与长度、DMA、回调和异步缓冲区必须同时检查生命周期、所有权、对齐和有效范围；判空不能替代这些检查

### 8. 中断安全
ISR 中遵循"三不"原则：
- 不调用阻塞函数（`HAL_Delay`、`HAL_I2C_Transmit` 等）
- 不获取互斥锁/信号量（除非使用 `FromISR` API）
- `volatile` 只解决编译器优化问题，不等于原子性或线程安全
- 多字节变量、复合状态和读改写操作必须使用临界区、原子操作、队列、通知或其他同步机制

### 9. 初始化顺序
严格遵循 时钟 → GPIO → 外设 → 中断 的初始化顺序：
- 反初始化严格逆序执行
- 模块 init() 时显式检查依赖句柄是否就绪
- 不依赖隐式的 main 调用顺序

### 10. 错误传播
错误必须被显式处理：
- 所有错误路径有 return 或错误处理
- 错误码逐层向上传播，禁止静默吞没
- 每个 `if (err)` 分支都有对应处理
- 外设 HAL 操作后检查返回值
