# 项目代码审查门禁

本门禁适用于 AI 生成、代码生成器产物、插件要求修改、人工新增、人工修改和已有代码重审。
其中，插件生成代码和插件要求修改的代码属于插件质量硬门禁范围，必须完整执行插件的命名、函数、注释和格式规则；
“生成代码”不再只是来源标签，而是决定质量约束强度的审计属性。

## 插件硬门禁范围

开始审查前必须给每个变更文件标记以下来源之一：

| 来源 | 适用规则 | 失败处理 |
| --- | --- | --- |
| 插件生成代码 | 完整执行 `style-profile.md` 的命名、函数、注释和格式规则 | 任一项失败即阻塞 |
| 插件要求修改的代码 | 对本次涉及的文件名、函数、代码块、新增符号和注释完整执行同一规则 | 任一项失败即阻塞 |
| 既有无关代码 | 保留既有写法，记录基线，不扩大检查范围 | 不得用作前两类的豁免 |

目标工程可以提供更严格的规则，但不能以较宽松的 `.clang-format`、相邻旧代码或既有命名基线降低插件硬门禁。

## 报告类别

| 类别 | 依据 | 示例 |
| --- | --- | --- |
| 风格 | 已确认的项目 profile | 缩进、括号、命名或注释不一致 |
| 功能 | 接口契约、调用链和测试 | 错误码遗漏、资源所有权错误、边界遗漏 |
| 安全 | 上下文、数据手册和并发证据 | ISR 阻塞、DMA 缓冲区不安全、数组越界 |

## 检查顺序

1. 确认审查范围、代码来源、profile（按 [style-profile 编码规范](style-profile.md) 的硬性约束）和可复现构建/测试命令；
2. 先检查编译、接口、错误路径和资源所有权；
3. 再检查 ISR/DMA/并发、数组边界及硬件约束；
4. 最后报告 profile 偏差，并注明其来源；
5. 按 style-profile 硬性约束核对：新文件的分层命名、禁用/允许的文件后缀、`g_/s_/p_/pf_` 变量前缀、公共 `.h` 函数声明和核心 `.c` 函数的完整 Doxygen（`@brief`/`@param`/适用的 `@retval`，按需使用 `@note`/`@warning`）、相似 `.c` 函数的说明去重、函数内部必要 `/* ... */` 注释的起止列对齐、整齐对齐的普通行尾注释、名称的可读性/可搜索性/领域语义与统一 TAB/Allman/列对齐排版。插件生成和插件要求修改的范围全部按上述规则判定失败即阻塞；既有文件仅对无关区域保留基线。用户或目标工程更严格的约定可以叠加，但不得降低插件硬门禁。
