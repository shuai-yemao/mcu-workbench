# 架构设计与嵌入式逻辑推理训练

## 训练目标

让用户从“代码现在是这样”进一步推导出“为什么这样组织、边界在哪里、替代方案是什么、如何验证”。训练必须建立在真实代码、配置、构建结果或运行证据上；没有证据的设计建议标记为目标设计或待验证假设。

## 推理链

按以下顺序推进，每轮只处理一个环节：

1. **问题**：系统或模块要解决什么具体问题？不解决什么问题？
2. **上下文**：调用者、被调用者、硬件、RTOS、构建配置和运行环境是什么？
3. **职责**：每个模块拥有哪项职责，哪项职责不能继续向上或向下泄漏？
4. **关系**：依赖方向、数据流、控制流、所有权和生命周期如何组织？
5. **约束**：实时性、并发、内存、功耗、错误恢复、可测试性和芯片差异如何限制方案？
6. **方案**：列出至少两个可行方案，明确接口、改动范围和验证成本。
7. **取舍**：当前方案为什么适合当前项目，牺牲了什么，未来何时需要重新评估？
8. **验证**：分别定义静态、构建、运行日志、板级和回归验证证据。

## 嵌入式架构检查表

- APP 是否只组织业务和用户场景，而没有偷偷承载硬件细节；
- Middleware、OS、BSP、Core、Driver 的职责和依赖方向是否清楚；
- 硬件差异是否集中在合理的 Port、Wrapper 或 BSP 边界；
- ISR、任务和普通调用上下文是否被区分；
- 缓冲区、句柄、队列和函数指针的所有权是否明确；
- 初始化、运行、错误恢复和去初始化是否形成完整生命周期；
- 接口是否暴露了不必要的底层类型、宏或时序假设；
- 替换芯片、RTOS、传感器或通信链路时，变化是否集中且可验证。

## 训练方式

先让用户画出或口述当前架构，再依次追问边界、依赖、约束和取舍。用户提出设计方案时，要求先写“设计目标、非目标、假设、方案、风险、验证”，再讨论 API 或文件名。对已有代码进行评价时，区分“现状描述”和“目标重构”，不把理想架构说成当前事实。

## 通过标准

用户能够用一条因果链解释：问题是什么 → 为什么这样分工 → 数据和控制如何流动 → 哪些约束影响了方案 → 有哪些取舍 → 如何证明方案有效。只说“解耦、可扩展、方便维护”等口号，不算通过。
