# 三层学习深度模型

项目驱动学习的核心原则之一：**学习深度由项目需求决定，而非由知识体系的完整性决定。** tutor 不在第一次接触时就追求完整掌握，而是根据知识在项目中的出现频率和角色控制推进深度。

## 三层定义

| 层级 | 目标 | tutor 行为 | 停止条件 |
| --- | --- | --- | --- |
| **L1 会用** | 让当前功能跑起来 | 只问基本概念、最小配置、使用条件、验证方式和常见错误 | 能初始化、能启动、能判断完成、能识别最常见错误 |
| **L2 理解** | 理解为什么这样配置、内部如何工作 | 追问配置原因、内部机制、边界条件、失败场景 | 能说明关键参数的决定因素、数据覆盖/竞争等边界条件、失败时的排查路径 |
| **L3 系统掌握** | 形成可迁移、可设计的深度理解 | 要求读 Datasheet/Reference Manual/源码，进行方案比较和架构设计 | 能独立设计方案、优化性能、解决复杂问题并迁移到新平台 |

## 深度提升触发条件

只有满足以下条件之一时，才从当前层级提升到下一层：

- 该知识在项目中**重复出现**（第二次遇到时进入 L2）；
- 该知识已成为当前**能力瓶颈**（无法绕过）；
- 后续工作**高度依赖**该知识；
- 需要**性能优化或架构设计**。

不满足提升条件时，完成当前层级即可回到项目开发。tutor 不主动加深。

## 初始深度判断

开始学习一个新知识时，先判断当前应进入哪一层：

```text
该知识是否阻塞当前任务？
├─ 是 → L1 会用（立即学习，只学够用）
│      完成后判断：是否在项目中重复出现？
│      ├─ 否 → 回到项目，记入 Learning Backlog
│      └─ 是 → 提升到 L2
└─ 否 → 记入 Learning Backlog，继续开发
```

## L1 会用：最小必要学习清单

第一次接触一个技术时，只回答以下问题，回答完就回到项目：

1. 它是什么？
2. 当前项目为什么需要它？
3. 最小配置是什么？
4. 数据/功能如何启动？
5. 如何判断完成/成功？
6. 当前功能如何验证？
7. 最常见错误是什么？

不要求理解底层机制。tutor 在 L1 阶段的问题以这 7 项为上限。

## L2 理解：深入追问清单

当知识在项目中第二次出现时，进入 L2。追问方向：

- 为什么使用当前配置（而非其他选项）？
- 内部如何工作（数据流、控制流、时序）？
- 不同方案有什么区别？
- 有哪些边界条件（缓冲区溢出、数据覆盖、竞争、超时）？
- 哪些情况下会失败？失败时现象是什么？

## L3 系统掌握：系统学习清单

当知识反复出现或成为瓶颈时，进入 L3。学习来源：

- Datasheet / Reference Manual
- 官方文档和协议标准
- 源码实现
- 经典书籍
- 底层实现机制

L3 阶段 tutor 要求用户形成方案设计、性能分析和跨平台迁移能力。

## 停止条件

满足以下全部条件时，tutor 停止当前知识的学习，让用户回到项目：

- 当前问题已经解释清楚；
- 有明确实现方案；
- 可以写最小实验；
- 实验结果可以验证；
- 知道失败时从哪里排查。

不要求"把这个领域全部搞懂"。用户出现知识扩张倾向时（从一个知识点不断延伸到更底层的基础领域），tutor 应主动提醒停止条件。

## 与 tutor 流程的集成

- tutor 模式开始时，先判断目标知识处于哪一层，在会话状态中记录 `learning_depth: L1|L2|L3`；
- L1 阶段每轮问题对应"最小必要学习清单"中的一项，不引入 L2 内容；
- L1 完成后，询问用户是否在项目中重复遇到该知识；若否，记录到 Learning Backlog 并结束本次学习；
- L2/L3 阶段恢复 tutor 模式的完整提问流程（见 [question-bank.md](question-bank.md)）；
- 架构推理（见 [architecture-reasoning.md](architecture-reasoning.md)）仅在 L2/L3 阶段启动。
