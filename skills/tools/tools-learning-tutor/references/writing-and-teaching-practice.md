# 技术文档、技术博客与授课表达训练

## 使用原则

每次选择一个输出目标，不把技术文档、技术博客和教学讲解混为一种写法。先保留用户原稿，再给短反馈和修正版；反馈应指出事实、结构、读者和可验证性问题，而不是直接代写全部内容。

## 技术文档训练

面向同组工程师，要求内容可以指导接入、修改和验证：

1. 目的与非目标；
2. 适用范围、前置条件和依赖；
3. 模块职责、接口和数据所有权；
4. 初始化、正常调用、错误处理和释放顺序；
5. 时序、并发、资源和硬件约束；
6. 代码/配置证据和验证步骤；
7. 已知限制、迁移影响和未验证项。

文档练习题：

> 请把刚才的机制写成一段同组工程师可以据此接入和验证的模块说明，至少包含职责、接口、调用顺序、一个失败路径和验证方法。

## 技术博客训练

面向不了解当前项目但具备基础编程知识的读者，采用以下顺序：

1. 真实问题或现象；
2. 如果没有该机制会怎样；
3. 直观模型和关键术语；
4. 真实代码调用链或最小示例；
5. 常见误区和边界；
6. 可迁移的工程结论。

博客练习题：

> 请用“问题 → 原理 → 代码证据 → 常见错误 → 可迁移结论”写一个面向初学者的短博客提纲，不要只罗列 API。

## 教学讲解训练

面向只掌握前置知识、但不了解当前机制的学习者，要求：

- 先确认对方已有的知识；
- 从一个最小问题或现象开始；
- 一次只引入一个新概念；
- 使用项目中的真实例子；
- 每讲一步就用一个问题检查理解；
- 根据对方回答决定补充、纠正还是继续；
- 最后让对方迁移到另一个调用路径或失败场景。

教学练习题：

> 假设学生只知道 C 函数和结构体，但不了解这个机制。请设计一个 3 分钟讲解顺序，并写出你会用来检查理解的第一个问题。

## 评价维度

| 维度 | 通过表现 |
| --- | --- |
| 事实准确 | 结论有代码、配置、测试或明确的用户操作证据 |
| 结构清晰 | 读者能看出问题、机制、边界和结论的关系 |
| 工程可执行 | 工程师知道如何接入、修改、排错和验证 |
| 读者适配 | 技术深度、术语和示例符合目标读者 |
| 逻辑推理 | 能说明因果、约束、取舍和替代方案 |
| 教学迁移 | 能引导对方复述，并把机制迁移到新场景 |

## 反馈格式

```text
表达目标：技术文档 / 技术博客 / 教学讲解
读者对象：
做得好的地方：
事实或证据缺口：
结构或逻辑缺口：
读者理解障碍：
下一次只改进的一点：
修正版：
```
