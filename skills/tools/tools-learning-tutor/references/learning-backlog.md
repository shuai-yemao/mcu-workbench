# Learning Backlog

项目开发过程中不要看到新知识就立即学习。建立一个独立的 Learning Backlog，将非阻塞知识暂存，避免频繁从开发状态切换到学习状态。

## 三层优先级

| 优先级 | 判断方式 | 处理时机 |
| --- | --- | --- |
| **阻塞** | 不懂就无法继续当前任务 | 立即进入 L1 学习（见 [learning-depth.md](learning-depth.md)） |
| **高频** | 当前可以绕过，但后续会反复使用 | 近期补充，不中断当前任务 |
| **后续** | 有价值，但不影响当前项目 | 记录，后续系统学习 |

## 判断原则

判断一个知识点的优先级时，不要问"这个知识重要吗"，而要问：

> **这个知识是否影响当前项目继续推进？**

示例：

```text
SPI 时序看不懂，驱动无法运行       → 阻塞
FreeRTOS Mutex 后面多个模块都会用   → 高频
想进一步研究 Cortex-M 异常入口实现  → 后续
```

## Backlog 条目格式

每个条目至少记录：

| 字段 | 内容 |
| --- | --- |
| 知识点 | 技术名称或概念 |
| 优先级 | 阻塞 / 高频 / 后续 |
| 出现场景 | 在哪个项目任务中遇到，什么现象触发的 |
| 当前已知 | 用户已经掌握的部分 |
| 缺口 | 具体不知道什么 |
| 出现次数 | 在当前项目中出现的次数 |
| 首次日期 | 第一次记录的时间 |
| 状态 | 待学习 / 学习中（L?） / 已掌握（L?） |

## 优先级提升条件

一个知识进入 Backlog 后，只有满足以下条件之一才提升优先级：

```text
阻塞当前任务
    或
在项目中重复出现（出现次数 >= 2）
    或
已经明显成为能力瓶颈
```

出现次数达到 2 时，tutor 应提醒用户：该知识已从"高频"候选提升为可进入 L2 学习的对象。

## 与会话状态的集成

Learning Backlog 存储在会话状态中（见 [session-state.md](session-state.md)）。tutor 在以下时点更新 Backlog：

1. **扫描阶段**：发现项目中使用了用户不熟悉的技术时，初步记录；
2. **学习过程中**：发现当前学习目标之外的关联知识时，记入 Backlog 而非立即展开；
3. **学习结束后**：将已完成学习的条目标记为"已掌握"，记录掌握层级；
4. **会话恢复时**：先展示 Backlog，让用户选择继续哪个知识点的学习。

## 跨项目学习路线

每个项目结束后，整理 Backlog 中出现的知识点。反复出现的知识（出现次数 >= 2）是最值得进行 L3 系统学习的方向。

```text
Project A: DMA, UART, FreeRTOS Queue, SPI
Project B: DMA, FreeRTOS Mutex, SPI, HardFault
Project C: DMA, Mutex, Race Condition, HardFault

→ DMA(3次), FreeRTOS(3次), 并发问题(2次), HardFault(2次)
→ 这些就是个人系统学习的优先路线
```

个人学习路线不由课程目录决定，而由项目暴露出的能力缺口决定。tutor 在项目结束整理时，应指出跨项目重复出现的知识点并建议提升到 L3。

## 与笔记的关系

Learning Backlog 是学习管理工具，不是学习笔记本身。Backlog 条目只记录"学什么、何时学、学到什么程度"，具体的学习内容仍按 [note-template.md](note-template.md) 沉淀到 Obsidian 笔记中。
