# 基于 Obsidian 知识笔记的教学章节与提问模板

## 栏目权威与提问原则

1. 用户指定的 Vault 模板优先；[note-template.md](note-template.md) 只提供默认结构。
2. 每个问题必须服务于一个明确的笔记栏目；先标注“将写入哪里”，再提问。
3. 每轮只问一个最小问题，不在问题中给出答案或混合多个概念。
4. 先从代码、配置、测试或用户实际操作中取证；没有证据时标为未验证，不以常识补写。
5. 引言在全部栏目完成后再凝练；总结必须优先采用用户自己的复述。

## 单题循环

1. 选择当前笔记栏目中尚未确认的一个事实、关系或理解缺口。
2. 给出必要的 `file:line`、现象或操作证据，并说明本题对应的栏目。
3. 提出一个开放问题，等待用户回答。
4. 将回答判为“已理解、部分理解或待补齐”；保留原回答。
5. 部分理解时给不超过 100 字的纠正，再问一个只验证该缺口的问题；回答“不知道”时给不超过 50 字的最小解释，记录薄弱点后继续。
6. 将已确认结论、用户表述、证据和未验证项分别写入会话状态与对应栏目。

## 栏目主流程

引言在其余栏目完成后生成；其余栏目按下面的 Obsidian 模板顺序推进。若用户指定的模板栏目不同，以用户模板为准，并在会话状态中记录映射关系。

## 与默认 Obsidian 模板对齐的提问表

| 笔记栏目 | 该栏目要形成的产物 | 单题模板 | 通过证据 |
| --- | --- | --- | --- |
| 标题与一句话定义 | 对象、职责和边界 | “请用一句话说明它是什么、负责什么，以及不负责什么？” | 用户能说出对象、职责和至少一个边界。 |
| 实际意义 | 要解决的问题与代价 | “没有它时，当前项目会在哪个具体环节变复杂、出错或无法完成？” | 能关联真实痛点，而非泛泛说‘解耦’。 |
| 应用场景 | 至少两个项目内路径 | “从已扫描的路径中，哪两处使用了它？各自要达成什么结果？” | 路径、调用者和目标可由证据定位。 |
| 核心逻辑/原理 | 真实机制链路 | “在这一步，谁触发、谁保存或处理数据、条件是什么、结果由谁消费？” | 能说明角色、关系、时序和结果。 |
| 关键公式/结论 | 参数、约束或可迁移结论 | “这个值/规则由什么决定；改变它会影响什么？” | 有代码、配置或文档依据；未知值明确标未验证。 |
| 实际操作步骤 | 可复现操作 | “若从零开始验证该能力，第一步要准备什么，成功如何观察，失败怎样处理？” | 顺序、观察点和异常处理完整。 |
| 常见问题 | 现象到验证的闭环 | “若这里失效，最可能看到什么现象？先检查哪条证据来区分根因？” | 包含现象、根因、修复和验证。 |
| Q&A：基础 | 概念与直接用法 | “它的输入、输出和最小使用条件分别是什么？” | 不混淆对象、动作和结果。 |
| Q&A：进阶 | 边界与易混点 | “这两个相近概念分别描述什么，在哪个阶段才会出现差异？” | 能说明区别、条件和后果。 |
| Q&A：困难 | 设计取舍与迁移 | “若把场景替换为另一条调用路径，哪些不变，哪些必须重新设计？” | 能基于机制迁移，不只复述例子。 |
| 总结 | 用户自己的整体复述 | “请用 3–5 句话串起它是什么、为何需要、如何工作及主要取舍。” | 覆盖定义、价值、机制和边界。 |
| 参考资料 | 可追溯来源 | “这个结论分别由哪份代码、文档、测试或操作记录支持？” | 每项资料说明支持的结论。 |

## 机制映射题

当学习目标涉及回调、事件、中断、消息、状态机、任务协作或类似机制时，不直接询问 API 名称；按缺口逐个提问以下角色：

1. 触发源：什么条件或执行路径启动该机制；
2. 参与者：创建者、注册者、处理者、结果消费者各是谁；
3. 关系与所有权：配置、处理函数、上下文数据分别由谁保存和释放；
4. 选择条件：筛选条件、状态、优先级或路由规则是什么；
5. 时序与数据：输入如何进入、何时处理、输出如何影响下一步；
6. 边界：取消、失败、重复触发、并发或资源失效时如何表现。

通过标准：用户能用 2–3 句话说明当前机制的角色、触发链路和设计意图；只复述函数名、只描述现象或只使用抽象口号均不通过。

## Q&A 规则

- 教学栏目结束后再进入 Q&A；总数 3–6 题，基础/进阶/困难各 1–2 题；
- 优先覆盖会话中的犹豫、错误、未验证项和代码中的边界；
- 逐题等待回答，记录用户原答、修正后理解、对应栏目和证据；
- 不在问题中泄露答案；仍未理解时记录薄弱点，不把跳过视为掌握。
