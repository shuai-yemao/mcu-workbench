# 项目 Git 管理

## 职责与边界

统一处理 Git 原生生命周期及其可审计证据：仓库状态、分支、worktree、精准暂存、提交、合并/变基、标签、远端同步、冲突和受控恢复。

只处理 Git；不调用 GitHub、GitLab、Gitee 的 PR、Issue、CI 或发布 API，不替代 `tools-quality`、`tools-build`、`tools-release` 的实际验证，也不新增 Node CLI 或自动执行脚本。

## 开始前：先只读发现

1. 识别当前目录对应的仓库根、当前 worktree、当前分支、上游、远端、工作区状态和未暂存/已暂存差异。
2. 检查嵌套 Git 仓库、已有 worktree、`.gitmodules` 与 Git LFS 配置。普通仓库、嵌套仓库识别和 Git worktree 可处理；发现 submodule 或 LFS 时只报告边界，不直接操作。
3. 读取项目既有的保护分支、分支模型、命名规范和贡献说明。若其与本 Skill 的约定冲突，报告差异并等待用户选择，绝不擅自迁移模型或改写规则。
4. 任何会改变 Git 状态的动作之前，先给出目标、预期文件范围、命令、影响和可恢复性，等待明确确认。

执行安全与确认细节时读取 [`安全操作契约`](references/git-safety-contract.md)。分支、提交与生命周期决策读取 [`Git 生命周期工作流`](references/git-lifecycle-workflow.md)。需要判断嵌入式工程验证交接时读取 [`嵌入式验证交接`](references/git-embedded-handoff.md)。

## 提交关卡

当一个变更集只服务单一目标、文件范围可说明并且可独立回滚时，提示“建议提交”。不因单个文件保存、无关格式化或多个 Jira 需求混在一起而提示提交。

相关验证已运行时记录实际结果；验证尚未执行时允许在用户确认后提交，但必须明确标记“验证待补”，不得声称已通过。

## 固定证据报告

每轮操作按以下结构输出：

```markdown
## 执行边界
- 仓库根、worktree、当前分支和请求目标

## 发现状态
- 上游/远端、工作区与暂存区状态、相关文件范围

## 确认记录
- 用户已确认的写操作；未确认动作保持未执行

## 已执行命令与结果
- 逐条命令、退出状态和产生的提交/标签 ID

## 验证与交接
- 已运行验证、验证待补，以及 tools-quality/tools-build/tools-release 建议

## 未执行的高风险操作
- 目标、影响、恢复路径和下一步确认项
```

不要把命令建议、静态检查、主机构建、目标板运行或硬件验证混为同一种结论。
