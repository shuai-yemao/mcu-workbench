# Review 输入/输出契约

本 Skill 对最终代码、补丁或 `git diff` 做 Spec 优先的独立审查。它必须重新读取 `spec.md`，逐条核对范围、业务规则和验收标准，运行测试、类型检查和构建，最后调用 `tools-quality` 的 `mode: final-gate` 形成最终代码质量出口，并为每条要求提供代码或测试证据。发现直接对应已批准 Spec 且不扩大范围的遗漏时，必须先补充能证明当前行为缺失的测试/检查，完成最小修复后重新验证；任务勾选状态不构成完成证据。

## 输入

每次审查必须附带以下输入：

1. 最终代码/变更集：目标文件路径、补丁或 `git diff`，以及可复现的构建/测试命令；
2. 相关接口与约束：当前接口、资源所有权、错误处理与硬件约束；
3. `spec.md`：放行后的 Spec 绝对路径和版本；审查时必须重新读取全文，不能只使用摘要或任务状态；
4. 验证入口：项目测试、类型检查和构建命令，绝对工作目录、工具版本、产物路径及适用的专项检查；无独立类型检查时必须记录批准的等效静态检查和原因；
5. 代码质量门禁报告：`tools-quality` `mode: final-gate` 的注释、格式、代码审查、Cppcheck/MISRA 结果、规则来源、工具版本和复检证据；
6. 格式检查配置证据：目标工程 `.clang-format`、`.editorconfig` 或其他已确认配置的路径和内容摘要；工程配置与插件规范不一致时，必须记录偏差，不能静默覆盖插件规范；
7. 上游交接链：若代码来自需求实施，提供 `plan.md`、`task.md`、逐项执行记录、RCP、`workflow-review-gate` 放行结论和实现层交接信息。`task.md` 的状态、勾选和“可交付”标记只作为上下文，不作为完成判据；用户直接提交现有 diff 审查时，明确该链路缺失，不得伪造。

## 输出

审查报告必须固定包含以下字段：

- 审查范围与证据：被审文件/变更集、证据来源与等级；
- Spec 逐条追踪矩阵：每条范围、业务规则和验收标准的 ID、摘要、代码证据、测试/检查证据、结果和未验证项；
- 代码质量门禁证据：`tools-quality` `mode: final-gate` 的注释、格式、代码审查、Cppcheck/MISRA 报告，记录规则来源、命令、绝对 cwd、工具版本、退出码和检查范围；
- 注释与格式摘要：记录文件头、公开 API Doxygen、`@param`、`@retval`、必要的 `@note`/`@warning`、关键步骤、中文注释和格式复检结果；
- 验证门禁证据：测试、类型检查、构建及适用专项检查的命令、绝对 cwd、工具版本、退出码和产物；
- 整改闭环证据：遗漏修复前的失败测试/检查、修复文件和理由、修复前后 `git diff` 审阅、重新验证结果；格式/必要注释整改单独列出；
- 按严重级别分组的问题：阻塞/高/中/低；
- 定位：`relative/path:line`；
- 影响：触发路径与失败后果；
- 修复建议：已执行的 Spec 遗漏修复、格式/注释整改分别列出；超出批准范围的问题只给建议并阻塞；
- 已执行/待补验证：测试/类型检查/构建以及静态/主机/目标运行/实物分别记录；
- 阻塞项与未验证假设；
- 最终门禁结论：`通过` 或 `阻塞`。每条 Spec 要求无代码/测试证据、测试/类型检查/构建任一失败或无法复现、格式/注释任一失败时必须为 `阻塞`；任务勾选状态不能单独支持通过。

## 契约要求

- 报告必须标明代码版本或 diff、审查基线、profile 来源及未验证假设。
- 格式和注释完整性是交付前必经检查，不得只凭肉眼或“代码可编译”宣称通过。
- 发现直接对应已批准 Spec 的遗漏时，必须先增加失败测试/检查，再进行最小修复并重新运行测试、类型检查、构建和 Spec 追踪；不得改变 Spec 范围、用户选择的方案、关键接口/资源所有权或引入未确认前提。
- 格式或必要注释初检失败时，必须执行受限整改和复检：只允许格式化及补充/更正必要注释；整改前后审阅 `git diff`，不得借此改变函数签名、控制流、常量/宏取值、数据结构、资源/错误路径、包含依赖或分层关系。
- 同条件复检与 `git diff --check` 未全部通过，或工具不可用、检查不可复现时，最终结论必须为 `阻塞`。
- 风格与静态规则优先级由 `tools-quality` 统一执行：用户明确要求、目标工程配置、相邻源码，最后才是项目 profile；任何偏差都必须记录。
- 不把静态检查或主机测试表述为板级验证。
- 不以 `task.md` 的勾选、状态、`可交付` 标记或执行记录替代 `spec.md` 的逐条核对。
- 测试、类型检查和构建必须有实际命令和退出码；缺少入口时记录原因和等效检查，不能伪造通过。
- 对 MCU Workbench 生成器产物、AI 生成代码、人工新增/修改代码和已有工程代码，统一交给 `tools-quality` 核对（覆盖 App、Service、Platform、Impl、Vendor 及其内部角色；公开函数 Doxygen、中文注释、80 列硬限制、格式和 Cppcheck/MISRA 规则），用户或项目明确采用其他约定时以该约定优先。
- 中间 Skill 调用 `tools-quality` 时使用 `mode: advisory`，只能返回阶段质量证据；最终代码必须由本 Skill 使用 `mode: final-gate` 复核，不能把阶段结果直接作为最终交付结论。
