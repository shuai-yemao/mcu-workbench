# 最终代码 Review 编排（输出前最后一层门禁）

## 职责

编排对已产出最终代码或变更集的 Spec 优先独立审查：先重新读取放行后的 `spec.md`，把范围、非目标、业务规则、状态/权限边界和验收标准拆成可追踪条目，再逐条寻找代码与测试证据。任务勾选状态、任务数量或 `task.md` 的“可交付”标记只作为施工上下文，不能证明需求完成。必须实际运行项目测试、类型检查和构建，并最后调用 [`tools-quality`](../../tools/tools-quality/SKILL.md) 的 `mode: final-gate` 形成最终代码质量出口；发现直接对应已批准 Spec、且不需要扩大范围或改变关键设计的遗漏时，先补充能证明缺失的测试/检查，再做最小修复并重新执行全部验证。任一质量复检、需求证据或验证门禁失败时，最终结论为阻塞。本 Skill 不得自行扩展 Spec、替换用户选择的方案或把静态/主机检查表述为板级验证。

## 触发时机

在以下时机触发：

- 实现 Skill（`app-architecture`、`platform_os`、`platform_bsp`、`impl_board`、`impl_bsp`、`platform_mcu`、`impl_os`、`vendor_mcu` 等）已输出最终代码、补丁或 `git diff`；
- `workflow-integration-plan` 在代码产物就绪后交接最终代码/变更集与验收清单；
- 用户要求对现有代码、补丁或 diff 做独立审查。

若输入仍处于需求或生成阶段，先交给 `workflow-review-gate`（需求/方案阶段）或对应实现 Skill；本 Skill 不承担代码生成阶段。

## 输入

1. 最终代码/变更集：目标文件路径、补丁或 `git diff`；prototype 请求不进入本 Skill；
2. 相关接口与约束：当前接口、资源所有权、错误处理与硬件约束；
3. 构建或测试入口：可复现命令、绝对工作目录与产物路径；
4. Spec 依据：放行后的 `spec.md` 绝对路径和版本；必须重新读取全文，不能只依据任务标题、勾选状态或上一次摘要；
5. 上游施工上下文：经用户选择和方案审查通过的 `plan.md`、`task.md`、`workflow-task-execution` 执行记录、`workflow-review-gate` 放行结论和上游交接信息。`task.md` 状态只用于解释施工上下文，不是最终完成判据；用户直接提交现有 diff 时，明确缺失的链路；
6. 验证入口：项目测试、类型检查和构建命令，绝对 `cwd`、产物路径和适用的目标验证入口；若没有独立类型检查命令，必须记录工程证据和获批准的等效静态检查，不能伪造类型检查通过；
7. 代码质量门禁输入：调用 `tools-quality` 的 `mode: final-gate` 所需的最终代码/diff、Spec 逐条追踪矩阵、目标工程 `.clang-format`/`.editorconfig` 或等效配置、Cppcheck/MISRA 配置、质量报告和 `tools-verification` 适用证据；记录规则优先级、工具版本和偏差。按 RCP 的 `spec_rigor` 和 `spec_overlays` 复核是否具备对应证据；`human_review` 必须有人工审查记录，`versioned` 必须有版本/负责人/依赖/变更记录。

## 审查流程

1. **范围与证据**：确认被审版本/diff、审查基线、目标工程根目录和变更范围；声明 `tool_root`、`firmware_root` 与每条命令的绝对 `cwd`。
2. **重读 Spec 并建立追踪矩阵**：逐条提取范围、非目标、业务规则、状态/权限边界和验收标准，为每条要求生成稳定 ID；禁止用 `task.md` 勾选、状态或“所有任务完成”替代 Spec 核对。
   同时核对 `spec_rigor` 是否与实际变更风险匹配；发现实际范围高于 Spec 力度时，必须阻塞并回传 Review Gate，不得以轻量文档放行高风险实现。
3. **先执行基线验证**：实际运行项目测试、类型检查和构建，记录命令、工具版本、退出码、产物绝对路径、SHA-256、重试次数和证据等级。任一入口不可发现、不可执行或失败，都必须进入阻塞/待修复记录。
4. **逐条核对实现证据**：对追踪矩阵的每条要求检查代码路径、符号、配置和测试用例；每行必须写出 `relative/path:line` 或测试文件/用例、命令和结果。明确区分通过、遗漏、冲突、未验证和不适用。
5. **遗漏修复闭环**：若遗漏直接对应已批准 Spec，且不改变范围、用户选择的方案、接口所有权或关键架构决定，先增加一个能证明当前行为缺失的测试/静态检查，再做最小实现修复；审阅修复前后 `git diff`，然后重新运行测试、类型检查、构建和受影响的专项检查。若需要扩大范围、改变 `plan.md`、修改 Spec 或补充关键决定，停止并阻塞回传上游。
6. **代码质量门禁**：由 `verification-engineer` 最后调用 `tools-quality` 的 `mode: final-gate`，按项目规则完成注释完整性、格式、代码审查、Cppcheck 和 MISRA 复核；质量 Skill 只能在最终证据齐全时输出最终 `通过` 或 `阻塞`。
7. **质量复检与专项审查**：消费 `final-gate` 的整改/复检结果；按项目代码审查门禁分离报告质量、功能、接口/资源所有权、ISR/DMA/并发、安全和分层问题，并核对调用链与资源生命周期。
8. **报告与交接**：由 `embedded-lead` 汇总 Spec 追踪矩阵、代码/测试证据、`final-gate` 结果、修复闭环、测试/类型检查/构建结果和未验证项；只有所有 Spec 要求有通过证据且 `final-gate` 与全部验证门禁通过时才可放行。

每个步骤只记录已执行的验证与证据等级；`firmware-engineer` 仅在需要澄清代码入口、数据流或可修改范围时参与，`toolchain-engineer` 仅在需要复现构建/测试时参与。

参与分工：`embedded-lead` 负责汇总与交接；`system-architect` 负责 Spec、接口、资源和分层核对；`verification-engineer` 负责测试、类型检查、格式/注释和并发审查；`toolchain-engineer` 负责复现测试、类型检查和构建；`hardware-integration` 负责板级、DMA 和硬件约束证据；`firmware-engineer` 仅在已批准范围内执行遗漏修复或澄清代码入口。若当前会话未分派 agent，由主会话执行相同职责，不得凭空声明已分派或已验证。

## 固定输出

审查报告必须包含：

- 审查范围与证据：被审文件/diff、版本、证据来源与等级；
- 代码质量门禁证据：`tools-quality` `mode: final-gate` 的注释、格式、代码审查、Cppcheck/MISRA 报告、规则来源、命令、绝对 cwd、工具版本、退出码和检查范围；
- 注释与格式摘要：文件头、公开 API Doxygen、参数/返回值、必要约束、关键步骤、注释语言和格式复检结果；
- Spec 逐条追踪矩阵：每条范围、业务规则和验收标准的 ID、原文摘要、代码证据、测试/检查证据、结果和未验证项；
- 验证门禁证据：测试、类型检查、构建及适用的专项检查命令、绝对 cwd、工具版本、退出码和产物；
- 整改闭环证据：遗漏修复前的失败测试/检查、修复文件与理由、修复前后 `git diff` 审阅、重新验证结果；格式/注释整改必须单独标明；
- 按严重级别分组的问题：阻塞/高/中/低；
- 定位：`relative/path:line`；
- 影响：触发路径与失败后果；
- 修复建议：已在批准范围内修复的遗漏和格式/注释问题逐项记录；超出范围或需上游决定的问题只给建议并阻塞；
- 已执行/待补验证：测试/类型检查/构建以及静态/主机/目标运行/实物分别记录；
- 阻塞项与未验证假设；
- 最终门禁结论：`通过` 或 `阻塞`。只有每条 Spec 要求均有代码或测试证据、测试/类型检查/构建及适用检查全部通过、整改后复检和 `git diff --check` 通过时才可通过；任务状态不得单独作为通过依据。

报告契约见 [Review 输入/输出契约](references/prompt-contract.md)。

## 修复与整改边界（硬规则）

- 本 Skill 可以修复直接对应已批准 Spec 的遗漏，但必须先补充能证明当前行为缺失的测试/检查，且修复不得扩大范围、改变用户选择的方案、改变关键接口/资源所有权或引入未确认的硬件/RTOS 前提。无法满足这些条件时必须阻塞并交回上游。
- 不把 `task.md` 的勾选状态、`可交付` 状态、任务数量或执行记录当作需求完成证据；它们只能解释变更来源和施工上下文。
- 功能遗漏修复完成后，必须重新运行测试、类型检查和构建，并重新生成 Spec 逐条追踪矩阵；不能只运行受影响的单测后宣布通过。
- 代码质量整改由 `tools-quality` 执行：中间阶段只允许 `advisory` 检查；最终阶段由 `final-gate` 复核，直接写回仍只限格式和必要注释；静态分析问题交回对应实现 Skill，不得借质量整改掩盖功能、接口、架构、安全或资源问题。
- 注释不得逐行复述代码、推测硬件事实或掩盖功能问题；语言遵从项目约定，未约定时使用中文。
- 未确认被审版本/diff 与审查基线前，不开始审查。
- 未重新读取 `spec.md`、未建立逐条追踪矩阵、任一要求缺少代码/测试证据、测试/类型检查/构建不可复现或失败时，不得放行。
- 如果最终代码反映了未写入最新 `spec.md` 的需求变化，必须判定为 `阻塞`，回传需求变更门禁；不得先接受代码、再要求补写 Spec。
- 必须执行 [SOLID 代码施工硬门禁](../workflow-review-gate/references/solid-code-gate.md)，逐项给出 SRP、OCP、LSP、ISP、DIP 的代码或测试/检查证据；任一适用原则缺少证据或不满足时，结论为 `阻塞`。
- 不将静态检查、主机测试或日志推断写成目标运行或实物验证结论。
- 不引用归档 workflow 或不存在的 agent 名称；迁移资料只见 [能力索引](references/capability-index.md)。
- 运行记录必须能区分工具仓库和固件仓库；命令、退出码、产物绝对路径与 SHA-256、证据等级和重试次数必须可追溯。
