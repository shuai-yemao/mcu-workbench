# SOLID 代码施工硬门禁

本文件是插件内代码设计与实现的统一硬门禁。所有会新增、修改或重构代码的
workflow 和实现层 Skill 都必须遵守；下游 Skill 可以补充领域规则，但不得降低本门禁。

## 五项原则

| 原则 | 代码施工要求 | 必须留下的证据 |
|---|---|---|
| SRP：单一职责原则 | 一个模块、类、函数或文件只承担一类稳定职责；业务策略、协议机制、硬件绑定、资源管理和验证逻辑不得无依据混在同一职责中。 | 职责边界、变更原因、调用者/被调用者和对应文件位置 |
| OCP：开放封闭原则 | 新增能力优先通过稳定接口、注册表、配置或新增实现扩展；不得为单个新设备反复修改稳定公共接口或复制已有核心逻辑。 | 扩展点、兼容性影响、已有调用方保持不变的证据 |
| LSP：里氏替换原则 | 具体实现必须可替换地履行抽象契约，不能偷偷改变返回值语义、错误处理、生命周期、阻塞、ISR、DMA、并发或资源所有权约定。 | 接口契约、实现差异、正常/异常路径测试或检查 |
| ISP：接口隔离原则 | 接口按使用者和能力拆分；调用者不应被迫依赖未使用的操作、类型或底层头文件，公共头只暴露必要契约。 | 调用者-接口映射、最小公开 API、依赖检查 |
| DIP：依赖倒置原则 | 高层依赖稳定抽象，具体 Driver、HAL、RTOS、芯片和板级资源由组合根或适配层注入；依赖方向保持 `App → Service → Platform ← Impl → Vendor`。 | 依赖图、注入点、include/调用链检查和边界测试 |

## 放行规则

1. 施工前，`workflow-review-gate` 必须在 `spec.md` 中记录本次变更适用的 SOLID 原则、范围内的设计约束和可验证证据；不适用的原则也要说明理由。
2. `workflow-integration-plan` 和 `workflow-task-breakdown` 必须把 SOLID 检查点映射到 `plan.md`、`task.md` 的方案/任务验收标准。
3. `workflow-task-execution` 每次只执行一个任务；先补能证明当前行为或边界缺失的测试/静态检查，再实现，并回写对应 SOLID 证据。
4. 任何原则无法满足、证据不足或需要突破既有分层/契约时，任务必须 `blocked`，交回需求审查或方案审查，不得自行放宽原则。
5. `workflow-final-review` 必须重新读取最新 `spec.md`，逐条核对五项原则和每条验收标准；缺少代码/测试/检查证据时不得放行。

## 与需求变化门禁的关系

SOLID 门禁约束“代码怎么设计”；需求变化门禁约束“什么时候允许施工”。若用户改变范围、业务规则、接口、资源边界或验收标准，必须先更新并重新放行 `spec.md`，再更新 `plan.md`、`task.md` 并恢复实现。不得用 SOLID 解释替代需求决策，也不得先改代码再补写 Spec。

## 固定交接字段

每次代码施工或审查都必须记录：

- `solid_status`：`pass` / `blocked`；
- 五项原则逐项结果：`pass` / `not_applicable` / `blocked`；
- `evidence`：`relative/path:line`、测试/静态检查命令、退出码和证据等级；
- `violations`：违反原则、影响范围和回传对象；
- `spec_version`：审查时实际读取的 `spec.md` 版本或提交。
